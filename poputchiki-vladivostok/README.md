# Попутчики во Владивосток

Сервис для поиска попутчиков среди туристов, едущих одним маршрутом (аэропорт,
центр, остров Русский и т.д.), чтобы разделить стоимость трансфера.

## Стек

- **Frontend**: форма заявки на китайском языке + публичная страница со списком
  заявок (`public/index.html`, `public/requests.html`), без сборки и фреймворков
- **Backend**: Node.js + Express (`server.js`)
- **База данных**: [Turso](https://turso.tech) — облачный SQLite-совместимый
  сервис (протокол libSQL, клиент `@libsql/client`). Локально для разработки
  Turso-аккаунт не нужен — без переменных `TURSO_*` в `.env` сервер сам
  работает с обычным файлом `data/db.sqlite`, тем же кодом и той же логикой.

## Быстрый старт

```bash
npm install
cp .env.example .env    # заполните ADMIN_PASSWORD; TURSO_* можно оставить пустыми
npm start                # сервер поднимется на http://localhost:3000
```

- Форма заявки: `http://localhost:3000/`
- Список всех заявок (публичный, без контактов): `http://localhost:3000/requests`
- Админ-панель: `http://localhost:3000/admin` (логин/пароль из `.env`, по умолчанию `admin` / `change-me`)

Файл базы данных для локальной разработки создаётся автоматически по пути
`data/db.sqlite` (см. `config.js`/`db.js`). В проде (Render) вместо файла
используется облачная база Turso — см. «Деплой на Render + Turso» ниже.

## Структура проекта

```
config.js       — настройки из .env (порт, параметры мэтчинга, учётные данные админки)
db.js           — подключение к Turso/libSQL и создание таблиц при старте
matching.js     — логика автоматического поиска совпадений
server.js       — Express-приложение и все роуты (публичные + админские)
public/
  index.html    — форма заявки (китайский язык, адаптивная)
  requests.html — публичный список всех заявок, без контактов (китайский язык)
  admin.html    — админ-панель (русский язык)
  admin.js      — клиентская логика админ-панели
  style.css     — общие стили
```

Код специально не разбит на множество мелких модулей — для проекта такого
размера роуты в одном `server.js` легче читать. Когда список эндпоинтов
вырастет, их можно вынести в `routes/requests.js` и `routes/admin.js`.

## Схема базы данных

- **requests** — заявки: `id, name, contact, travel_date, route_from, route_to, route_stops, people_count, comment, consent, status, created_at`.
  Статус: `new` (новая) → `matched` (есть совпадение) → `confirmed` (подтверждена) / `rejected` (отклонена).
- **groups** — группы попутчиков: `id, travel_date, route_from, route_to, route_stops, total_people, price, status, created_at, confirmed_at`.
- **group_requests** — связующая таблица «какие заявки входят в какую группу» (many-to-many).

> Отличие от исходного ТЗ: вместо текстового поля `request_ids` в `groups`
> использована отдельная таблица `group_requests`. Так проще и надёжнее
> делать JOIN'ы, не нужно парсить список id из строки вручную.

### Маршрут — несколько точек, а не только «откуда/куда»

Маршрут может состоять из нескольких точек по порядку («сложный маршрут»,
как у авиакомпаний): например `["机场", "俄罗斯岛", "市中心"]`. Реальный
«ключ маршрута» — колонка `route_stops` (JSON-массив точек в нужном порядке).
`route_from`/`route_to` остаются в схеме как первая/последняя точка — это
удобно для сортировки и для отображения в местах, где полный список не нужен;
не храним их избыточно ради читаемости, а держим синхронизированными при
каждой записи (форма → `server.js` → `db.js`).

На форме (`public/index.html`) список готовых точек — не жёсткое
перечисление «откуда-куда», а конструктор: выбираешь точку из списка,
жмёшь «+ 添加», она попадает в список ниже; так добавляется сколько угодно
точек (до `MAX_ROUTE_STOPS = 6` в `server.js`), в порядке добавления.
Готовые точки сейчас: 机场 (аэропорт), 市中心 (центр), 火车站 (вокзал),
俄罗斯岛 (остров Русский), 灯塔 (Токаревский маяк), 鹰巢山观景台
(смотровая «Орлиное гнездо»), 海洋水族馆 (океанариум) — плюс «其他» для
свободного ввода. Список — справочник для формы, сервер его не навязывает
(валидирует только длину/непустоту точек, не сверяет со списком).

## Логика мэтчинга (см. `matching.js`)

После сохранения новой заявки со статусом `new` система:

1. Ищет другие заявки со статусом `new` с тем же маршрутом (`route_stops`
   совпадает буквально — вся цепочка точек в том же порядке) и датой в
   пределах `DATE_TOLERANCE_DAYS` дней (по умолчанию ±1 день).
2. Жадно (greedy) набирает из них группу по порядку подачи заявок, пока
   суммарное число человек не достигнет `MAX_GROUP_SIZE`.
3. Если в группу попала хотя бы одна **другая** заявка (не только исходная)
   и итоговая сумма человек в диапазоне `[MIN_GROUP_SIZE, MAX_GROUP_SIZE]` —
   создаётся запись в `groups`, все участвующие заявки переводятся в статус
   `matched`. Никаких push-уведомлений об этом не отправляется — статус
   виден в публичном списке заявок (`/requests`) и в `/admin`, администратор
   просто периодически туда заглядывает.

Все три параметра (`MIN_GROUP_SIZE`, `MAX_GROUP_SIZE`, `DATE_TOLERANCE_DAYS`)
настраиваются через `.env` без изменения кода.

### Частичные совпадения (см. `findPartialMatches` в `matching.js`)

Кроме точного авто-мэтчинга, в админ-панели (`/admin`, раздел «Возможные
частичные совпадения») отдельно показываются пары заявок со статусом `new`,
у которых:
- дата близка (в пределах `DATE_TOLERANCE_DAYS`), и
- маршруты пересекаются хотя бы в одной точке, но не совпадают целиком.

Например «机场→俄罗斯岛→市中心» и «灯塔→俄罗斯岛» — разные маршруты, но у обоих
есть 俄罗斯岛, и даты рядом. Это не авто-группировка — просто подсказка
администратору, что этим двоим, возможно, стоит списаться и договориться
скорректировать маршрут, чтобы поехать вместе. Решение и создание группы
(кнопка «Создать группу из этих двух», использует тот же `POST
/api/admin/groups`, что и обычное ручное объединение) — за администратором.
Публично (в `/requests`) частичные совпадения не показываются — только в
защищённой паролем админке, без раскрытия чужих контактов посторонним.

**Осознанные ограничения первой версии** (легко расширить позже):

- В кандидаты на мэтчинг берутся только заявки со статусом `new` — уже
  собранные группы (`matched`/`confirmed`) автоматически не трогаются и не
  пересобираются. Если авто-мэтчинг что-то не поймал (например, стоило
  объединить заявку с уже подтверждённой группой) — админ делает это вручную
  через кнопку «Создать группу из выбранных».
- Маршрут (`route_stops`) сравнивается точным совпадением всей цепочки точек,
  включая порядок: "机场→俄罗斯岛→市中心" и "俄罗斯岛→机场→市中心" — разные
  маршруты. Для точек из готового списка это всегда работает одинаково; для
  «其他» (свой текст) два человека, напечатавшие адрес немного по-разному,
  не заматчатся автоматически — это можно улучшить позже (нормализация
  текста, fuzzy-поиск).

## Публичный список заявок (`/requests`)

Отдельная страница на китайском (`public/requests.html`), читает данные из
`GET /api/requests` — без авторизации, доступна всем. Показывает дату,
маршрут, число человек, статус, комментарий и время подачи заявки.

**Контакты (WeChat/телефон) на этой странице не отображаются** — сервер
их туда даже не отдаёт (см. `GET /api/requests` в `server.js`, там
отдельный `SELECT` без поля `contact`, в отличие от `GET /api/admin/requests`
для админки). Иначе номера телефонов и WeChat ID всех, кто подал заявку,
были бы видны любому в интернете. Если для вашего сценария это не
проблема (например, сервис работает в закрытой группе) и вы хотите видеть
контакты сразу в публичном списке — уберите `SELECT`-ограничение в этом
роуте, это одна строка.

**Устаревшие заявки скрываются из этого списка**, но не удаляются из БД —
в `/admin` они остаются видны (там нужна полная история). Скрываются:
- заявки, у которых `travel_date` уже в прошлом;
- заявки из групп, которые уже подтверждены (`confirmed`) или отклонены
  (`rejected`) — эти люди либо уже договорились, либо дело закрыто, им
  больше не нужно "искать" в публичном списке.

## Админ-панель

Простая защита паролем через HTTP Basic Auth (без сессий и cookie) —
логин/пароль задаются в `.env` (`ADMIN_USER` / `ADMIN_PASSWORD`).
Доступна на `/admin`:

- Таблица всех заявок со статусами и фильтром по статусу.
- Ручное создание группы из отмеченных заявок (когда авто-мэтчинг не сработал).
- Блок «Возможные частичные совпадения» — см. раздел выше.
- Установка/изменение цены поездки для группы.
- «Подтвердить группу» — переводит группу и её заявки в статус `confirmed`
  и показывает готовые тексты сообщений для каждого участника — их нужно
  скопировать и отправить вручную в WeChat (это заглушка первого этапа,
  см. `buildWeChatMessage` в `server.js`; позже сюда можно подключить
  реальный WeChat API).
- «Отклонить» — переводит группу и её заявки в статус `rejected`.

## Push-уведомления о новых заявках (ntfy)

При каждой новой заявке (`POST /api/requests`) сервер отправляет push-уведомление
через [ntfy](https://ntfy.sh) — бесплатный сервис пушей без регистрации, с
родным приложением на iOS и Android. Реализация — `notify.js`, обычный `fetch`
без сторонних библиотек (по той же схеме, что раньше был Telegram-бот).

**Настройка (один раз):**

1. Установите приложение **ntfy** из App Store (бесплатно).
2. Придумайте свой длинный случайный «топик» — по сути секретное имя канала:
   ```bash
   python3 -c "import secrets; print('poputchiki-vl-' + secrets.token_hex(8))"
   ```
   Не используйте простое слово: топик на публичном `ntfy.sh` не защищён
   паролем — кто узнает его имя, сможет присылать туда сообщения или их читать.
3. В приложении ntfy: **+** → **Subscribe to topic** → вставьте тот же топик,
   что и в шаге 2.
4. На сервере (в `.env` или в Variables на Railway) задайте:
   ```
   NTFY_TOPIC=poputchiki-vl-<ваша случайная строка>
   ```
   (`NTFY_SERVER` можно не менять — по умолчанию `https://ntfy.sh`.)

Если `NTFY_TOPIC` не задан — уведомление просто печатается в консоль сервера,
ничего никуда не отправляется (удобно для локальной разработки).

Каждое уведомление содержит маршрут, дату, число человек, имя и контакт
заявителя — то есть те же личные данные, что видны в `/admin`. Раз топик на
публичном сервере не имеет пароля, это разумный компромисс для личного
использования, но не полноценная защита — при повышенных требованиях к
приватности стоит рассмотреть self-hosted ntfy с авторизацией (см. их docs).

## Деплой на Render + Turso

Сервис переехал с Railway (там бесплатный период ограничен ~30 днями, после
чего без оплаты деплой останавливается) на связку, которая остаётся
бесплатной постоянно: **Render** (бесплатный Web Service) + **Turso**
(бесплатная облачная SQLite-база). Бесплатный план Render не даёт постоянный
диск — поэтому обычный файл SQLite там не годится, а Turso даёт тот же SQL
по сети (см. `db.js`).

Оба аккаунта создаются и настраиваются через веб-дашборд (GitHub-вход,
без установки чего-либо на телефон/компьютер), так же как раньше с Railway.

### Шаг 1 — создать базу на Turso

1. Зайдите на [turso.tech](https://turso.tech) и войдите через GitHub.
2. В дашборде создайте новую базу данных (**Create Database**), любое имя,
   например `poputchiki-vl`. Регион — ближайший к пользователям (например
   Токио/Сингапур для Владивостока, если доступен; иначе любой).
3. Откройте созданную базу → вкладка **Connect strings** (или аналогичная) —
   скопируйте **Database URL** (вид `libsql://poputchiki-vl-<org>.turso.io`).
4. Там же создайте **Auth Token** (кнопка **Create Token** / **Generate
   Token**) — скопируйте его, это секрет, который нужно будет вставить в
   переменные окружения на Render (шаг 3). Токен показывается один раз, если
   потеряли — создайте новый.

### Шаг 2 — создать Web Service на Render

1. Зайдите на [render.com](https://render.com) и войдите через GitHub —
   при первом входе разрешите Render доступ к нужному репозиторию (или ко
   всем репозиториям аккаунта).
2. **New** → **Web Service** → выберите этот репозиторий (`labuzin-maker/HTML`).
3. Репозиторий — монорепо (рядом лежат и другие проекты), поэтому обязательно
   укажите:
   - **Root Directory**: `poputchiki-vladivostok`
   - **Branch**: ветку, в которую пушится код сервиса (например
     `claude/server-connection-usjy08`, или `main`, если ветку туда смержили).
4. **Runtime**: Node. **Build Command**: `npm install`. **Start Command**:
   `npm start`.
5. **Instance Type**: Free.

### Шаг 3 — переменные окружения на Render

В настройках сервиса (**Environment** → **Environment Variables**) задайте
те же ключи, что в `.env.example`, кроме `PORT` (его выставляет сама Render):

- `TURSO_DATABASE_URL` — URL из шага 1.3.
- `TURSO_AUTH_TOKEN` — токен из шага 1.4.
- `ADMIN_USER`, `ADMIN_PASSWORD` — обязательно смените пароль с примера.
- `MIN_GROUP_SIZE`, `MAX_GROUP_SIZE`, `DATE_TOLERANCE_DAYS` — по желанию,
  иначе применяются значения по умолчанию (2 / 4 / 1).
- `NTFY_TOPIC` — если нужны push-уведомления о новых заявках, см. раздел
  «Push-уведомления о новых заявках (ntfy)» выше.

### Шаг 4 — деплой

Нажмите **Create Web Service** (или **Deploy** / **Manual Deploy**, если
сервис уже создан). Render соберёт проект (`npm install`), запустит
`npm start`; сервер при старте сам создаст нужные таблицы в Turso (см.
`initDb()` в `db.js`), отдельных миграций вручную гонять не нужно.

После деплоя откройте выданный Render домен (вид `https://<имя>.onrender.com`)
или подключите свой — `/` это форма, `/requests` публичный список, `/admin`
панель администратора (логин/пароль из шага 3).

### Важно про бесплатный план Render

Бесплатный Web Service на Render «засыпает» после ~15 минут без запросов и
«просыпается» за несколько секунд при следующем обращении (первый запрос
после простоя может быть на несколько секунд медленнее — это нормально,
не ошибка). Сами данные при этом не теряются: они живут в Turso, а не на
диске Render, так что сон/пробуждение контейнера на них не влияет —
в этом и была проблема с прежней схемой на Railway (файл на диске
контейнера), которую решает этот переезд.

## Возможные следующие шаги

- Реальная отправка сообщений в WeChat вместо копирования текста руками.

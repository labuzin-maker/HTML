# Попутчики во Владивосток

Сервис для поиска попутчиков среди туристов, едущих одним маршрутом (аэропорт,
центр, остров Русский и т.д.), чтобы разделить стоимость трансфера.

## Стек

- **Frontend**: форма заявки на китайском языке + публичная страница со списком
  заявок (`public/index.html`, `public/requests.html`), без сборки и фреймворков
- **Backend**: Node.js + Express (`server.js`)
- **База данных**: SQLite-файл через `better-sqlite3`, без внешнего сервера БД

## Быстрый старт

```bash
npm install
cp .env.example .env    # заполните ADMIN_PASSWORD
npm start                # сервер поднимется на http://localhost:3000
```

- Форма заявки: `http://localhost:3000/`
- Список всех заявок (публичный, без контактов): `http://localhost:3000/requests`
- Админ-панель: `http://localhost:3000/admin` (логин/пароль из `.env`, по умолчанию `admin` / `change-me`)

Файл базы данных создаётся автоматически по пути из `DB_FILE` (по умолчанию `data/db.sqlite`).

## Структура проекта

```
config.js       — настройки из .env (порт, параметры мэтчинга, учётные данные админки)
db.js           — подключение к SQLite и создание таблиц при старте
matching.js     — логика автоматического поиска совпадений
server.js       — Express-приложение и все роуты (публичные + админские)
public/
  index.html    — форма заявки (китайский язык, адаптивная)
  requests.html — публичный список всех заявок, без контактов (китайский язык)
  admin.html    — админ-панель (русский язык)
  admin.js      — клиентская логика админ-панели
  style.css     — общие стили
```

Код специально не разбит на множество мелких модулей — для проекта такого
размера роуты в одном `server.js` легче читать. Когда список эндпоинтов
вырастет, их можно вынести в `routes/requests.js` и `routes/admin.js`.

## Схема базы данных

- **requests** — заявки: `id, name, contact, travel_date, route_from, route_to, people_count, comment, consent, status, created_at`.
  Статус: `new` (новая) → `matched` (есть совпадение) → `confirmed` (подтверждена) / `rejected` (отклонена).
- **groups** — группы попутчиков: `id, travel_date, route_from, route_to, total_people, price, status, created_at, confirmed_at`.
- **group_requests** — связующая таблица «какие заявки входят в какую группу» (many-to-many).

> Отличие от исходного ТЗ: вместо текстового поля `request_ids` в `groups`
> использована отдельная таблица `group_requests`. Так проще и надёжнее
> делать JOIN'ы, не нужно парсить список id из строки вручную.

## Логика мэтчинга (см. `matching.js`)

После сохранения новой заявки со статусом `new` система:

1. Ищет другие заявки со статусом `new` с тем же маршрутом (`route_from` +
   `route_to` совпадают буквально) и датой в пределах `DATE_TOLERANCE_DAYS`
   дней (по умолчанию ±1 день).
2. Жадно (greedy) набирает из них группу по порядку подачи заявок, пока
   суммарное число человек не достигнет `MAX_GROUP_SIZE`.
3. Если в группу попала хотя бы одна **другая** заявка (не только исходная)
   и итоговая сумма человек в диапазоне `[MIN_GROUP_SIZE, MAX_GROUP_SIZE]` —
   создаётся запись в `groups`, все участвующие заявки переводятся в статус
   `matched`. Никаких push-уведомлений об этом не отправляется — статус
   виден в публичном списке заявок (`/requests`) и в `/admin`, администратор
   просто периодически туда заглядывает.

Все три параметра (`MIN_GROUP_SIZE`, `MAX_GROUP_SIZE`, `DATE_TOLERANCE_DAYS`)
настраиваются через `.env` без изменения кода.

**Осознанные ограничения первой версии** (легко расширить позже):

- В кандидаты на мэтчинг берутся только заявки со статусом `new` — уже
  собранные группы (`matched`/`confirmed`) автоматически не трогаются и не
  пересобираются. Если авто-мэтчинг что-то не поймал (например, стоило
  объединить заявку с уже подтверждённой группой) — админ делает это вручную
  через кнопку «Создать группу из выбранных».
- Маршрут `route_from`/`route_to` сравнивается точным совпадением строки.
  Для предустановленных вариантов из выпадающего списка это всегда работает
  одинаково; для варианта «其他» (свой текст) два человека, напечатавшие
  адрес немного по-разному, не заматчатся автоматически — это можно
  улучшить позже (нормализация текста, fuzzy-поиск).

## Публичный список заявок (`/requests`)

Отдельная страница на китайском (`public/requests.html`), читает данные из
`GET /api/requests` — без авторизации, доступна всем. Показывает дату,
маршрут, число человек, статус, комментарий и время подачи заявки.

**Контакты (WeChat/телефон) на этой странице не отображаются** — сервер
их туда даже не отдаёт (см. `GET /api/requests` в `server.js`, там
отдельный `SELECT` без поля `contact`, в отличие от `GET /api/admin/requests`
для админки). Иначе номера телефонов и WeChat ID всех, кто подал заявку,
были бы видны любому в интернете. Если для вашего сценария это не
проблема (например, сервис работает в закрытой группе) и вы хотите видеть
контакты сразу в публичном списке — уберите `SELECT`-ограничение в этом
роуте, это одна строка.

## Админ-панель

Простая защита паролем через HTTP Basic Auth (без сессий и cookie) —
логин/пароль задаются в `.env` (`ADMIN_USER` / `ADMIN_PASSWORD`).
Доступна на `/admin`:

- Таблица всех заявок со статусами и фильтром по статусу.
- Ручное создание группы из отмеченных заявок (когда авто-мэтчинг не сработал).
- Установка/изменение цены поездки для группы.
- «Подтвердить группу» — переводит группу и её заявки в статус `confirmed`
  и показывает готовые тексты сообщений для каждого участника — их нужно
  скопировать и отправить вручную в WeChat (это заглушка первого этапа,
  см. `buildWeChatMessage` в `server.js`; позже сюда можно подключить
  реальный WeChat API).
- «Отклонить» — переводит группу и её заявки в статус `rejected`.

## Деплой на Railway

Репозиторий — монорепо (в нём лежат и другие проекты рядом), поэтому Railway
нужно явно указать, из какой папки собирать этот сервис. `railway.json` в
этой папке задаёт билдер и команду запуска, но **Root Directory сервиса
всё равно нужно выставить руками** в дашборде Railway — это единственный
шаг, который нельзя сделать из репозитория.

1. **Root Directory**: в настройках сервиса (Settings → Source) укажите
   `poputchiki-vladivostok` — иначе Railway попробует собрать весь репозиторий
   целиком и не найдёт `package.json` в корне.
2. **Переменные окружения** (Settings → Variables) — задайте те же ключи, что
   в `.env.example`, кроме `PORT` (его выставляет сама Railway):
   - `ADMIN_USER`, `ADMIN_PASSWORD` — обязательно смените пароль с примера.
   - `MIN_GROUP_SIZE`, `MAX_GROUP_SIZE`, `DATE_TOLERANCE_DAYS` — по желанию,
     иначе применяются значения по умолчанию (2 / 4 / 1).
   - `DB_FILE` — **обязательно**, см. следующий пункт.
3. **Persistent Volume для базы данных** — это важно: файловая система
   контейнера Railway не сохраняется между деплоями без подключённого Volume,
   т.е. без этого шага база обнулялась бы при каждом redeploy/обновлении кода.
   - В сервисе: Settings → Volumes → Add Volume, точка монтирования, например
     `/data`.
   - Задайте переменную `DB_FILE=/data/db.sqlite` — тогда файл БД будет жить
     на смонтированном томе и переживать деплои.
4. Запушьте ветку в GitHub (или просто дождитесь авто-деплоя, если Railway
   уже подключён к репозиторию и веб-хук настроен) — Railway соберёт проект
   через Nixpacks (Node определится автоматически по `package.json`,
   `engines.node` там зафиксирован как `>=20`) и запустит `npm start`.
5. После деплоя откройте выданный Railway домен (или подключите свой) —
   `/` это форма, `/requests` публичный список, `/admin` панель администратора
   (логин/пароль из шага 2).

## Возможные следующие шаги

- Реальная отправка сообщений в WeChat вместо копирования текста руками.

- Автоматическое напоминание тем, чья заявка долго не находит пары.
- Экспорт заявок/групп в CSV для отчётности.
